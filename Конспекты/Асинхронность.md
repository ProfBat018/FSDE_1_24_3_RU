**Многопоточность, многозадачность, асинхронность и параллелизм в C#**

**Введение.** В современных приложениях часто нужно выполнять несколько действий одновременно или без задержек друг друга. Для этого используются приёмы **конкурентного программирования**: многопоточность, многозадачность, асинхронность и параллелизм. Эти концепции связаны, но не идентичны. В этом конспекте мы разберём каждую из них, покажем примеры на C#, и сравним подходы (например, Thread vs Task, Task vs async/await), чтобы понять их различия и область применения.

**Многопоточность**

**Многопоточность** – это способность программы иметь несколько потоков выполнения одновременно. _Поток_ (thread) — независимая последовательность инструкций внутри процесса. Каждый поток выполняется параллельно с другими (как минимум, создаётся иллюзия параллельности за счёт планировщика ОС). На многопроцессорных системах потоки могут реально выполняться одновременно на разных ядрах, что повышает производительность для вычислительно сложных задач.

Основные особенности многопоточности:

•**Параллельное выполнение:** несколько потоков могут выполняться одновременно, действительно параллельно (если есть несколько ядер) или псевдопараллельно (если ядер меньше, ОС чередует выполнение).

•**Общий адресный простор:** потоки внутри одного процесса разделяют память процесса, что позволяет им легко обмениваться данными, но требует аккуратной синхронизации.

•**Необходимость синхронизации:** при одновременном доступе нескольких потоков к общим данным нужны механизмы синхронизации (блокировки, мьютексы, семафоры и т.д.), чтобы избежать гонок данных и других ошибок.

•**Накладные расходы:** создание и переключение контекста потоков требует ресурсов. Слишком много потоков может привести к перерасходу памяти (каждый поток резервирует стек) и времени CPU на переключения.

В .NET для работы с потоками служит пространство имен System.Threading. Можно напрямую создавать и запускать потоки с помощью класса Thread. Ниже приведён простой пример создания потока и выполнения кода в фоне:

``` csharp
using System;
using System.Threading;

class Program
{
    static void Main()
    {
        Thread thread = new Thread(() =>
        {
            // Код, выполняемый во втором потоке
            Console.WriteLine("Второй поток: начинаю работу");
            Thread.Sleep(1000); // имитация длительной работы
            Console.WriteLine("Второй поток: работа завершена");
        });

        Console.WriteLine("Основной поток: запускаю второй поток");
        thread.Start(); // запускаем новый поток

        // Основной поток продолжает работу параллельно
        Console.WriteLine("Основной поток: выполняю работу пока второй поток занят");

        // Ждём завершения второго потока перед выходом (чтобы увидеть его вывод)
        thread.Join();
        Console.WriteLine("Основной поток: завершение программы");
    }
}
```

**Вывод (примерно):**

```bash
Основной поток: запускаю второй поток  
Основной поток: выполняю работу пока второй поток занят  
Второй поток: начинаю работу  
Второй поток: работа завершена  
Основной поток: завершение программы
```

В этом примере основной поток (тот, который выполняет Main) запускает дополнительный поток thread. Оба потока выполняются одновременно: пока второй поток “работает” (засыпает на 1 секунду), основной поток не стоит без дела – он выполняет свои инструкции. Метод thread.Join() в конце используется, чтобы основной поток дождался завершения фонового потока перед выходом из программы (иначе программа могла бы завершиться раньше, чем второй поток успеет вывести сообщение).

Использование нескольких потоков позволяет реально параллельно выполнять несколько задач. Например, в GUI-приложении можно запускать тяжелые вычисления в фоновом потоке, не блокируя UI-поток, чтобы интерфейс оставался отзывчивым. Однако при работе со _многопоточностью_ важно учитывать сложность: нужно правильно управлять доступом к разделяемым ресурсам и избегать ситуаций взаимной блокировки (deadlock). Кроме того, вручную создавать большое число потоков неэффективно – чаще используют _пул потоков_ (thread pool), который переиспользует ограниченное количество потоков для выполнения многих краткосрочных задач.

**Многозадачность**

**Многозадачность** – это способность операционной системы или среды выполнения запускать несколько **задач** одновременно (или быстро переключаться между ними). Термин “задача” в данном контексте обычно означает либо отдельные процессы, либо потоки внутри процесса. Многозадачность обеспечивает ощущение одновременной работы нескольких программ. Например, вы можете слушать музыку, пока работает браузер и скачивается файл – с точки зрения пользователя все эти задачи выполняются параллельно.

ОС реализует многозадачность, планируя время выполнения для каждого процесса/потока. Современные ОС используют **вытесняющую многозадачность**: каждый поток получает квант времени CPU, по истечении которого может быть приостановлен, чтобы дать шанс выполниться другим. За счёт этого даже на одном ядре процессора несколько задач прогрессируют “псевдопараллельно”. А на многоядерных системах процессы/потоки могут действительно выполняться в одно время на разных ядрах (что уже относится к параллелизму).

Важно отметить разницу: многозадачность – более общий термин, обычно относящийся к поведению всей системы (запуск нескольких независимых задач), тогда как многопоточность – один из способов реализации многозадачности _внутри одного приложения_. В контексте C#, многозадачностью можно считать ситуацию, когда ваше приложение выполняет несколько операций одновременно (например, обрабатывает сразу несколько клиентских запросов). Это может быть достигнуто с помощью многопоточности или асинхронности.

Простая аналогия: **многозадачность** – это когда жонглёр держит несколько мячей в воздухе (несколько дел в работе), а **многопоточность** – когда у жонглёра есть несколько рук (несколько потоков) для этого жонглирования.

**Асинхронность**

**Асинхронность** – это способ выполнять операции без блокирования текущего потока до их завершения. При асинхронном подходе программа может инициировать долгую задачу (например, запрос к серверу, чтение файла, вычисление) и не ждать пассивно, пока она закончится. Вместо этого можно продолжить выполнять другую работу, а к результату длительной операции вернуться позже, когда он будет готов. Асинхронное программирование повышает эффективность использования ресурсов и Responsiveness приложений, особенно когда дело касается ввода-вывода (I/O), где время ожидания значительно.

Чтобы лучше понять асинхронность, рассмотрим аналогию с бытовой задачей: **приготовление ужина**.

•_Синхронный подход:_ Вы ставите воду кипятиться и **ждёте**, пока она закипит, ничего больше не делая. Только после кипения воды начинаете резать овощи. Здесь каждая задача выполняется строго последовательно, следующая начинается лишь после полного завершения предыдущей. Время во время ожидания теряется впустую.

•_Асинхронный подход:_ Вы ставите воду на плиту и, **не дожидаясь кипения**, параллельно начинаете резать овощи. Когда вода закипит, вы переключаетесь обратно – добавляете макароны, затем продолжаете готовить соус и т.д. Вы не простаиваете в ожидании, а эффективно используете время.

В асинхронном сценарии выше фактически задействован **один человек**, выполняющий задачи без простоя, переключаясь между ними по мере готовности условий. В программировании асинхронность часто реализуется на **одном потоке**, который не блокируется на ожидании результата, а продолжает выполнять другие задачи (либо же отпускает управление _другим_ задачам/потокам). Асинхронность не обязательно подразумевает параллельное исполнение на разных ядрах – главное, что операции выполняются без ожидания друг друга.

В C# поддержка асинхронности реализована на уровне языка и библиотек. Можно выделить несколько подходов к написанию асинхронного кода: от ручного использования потоков до высокоуровневых средств async/await. Рассмотрим по порядку.

**Синхронное vs асинхронное выполнение**

При **синхронном** выполнении каждый вызов блокирует текущий поток до окончания. Например, если читать файл синхронно, поток исполнения остановится, пока весь файл не будет прочитан в память. В это время он не делает ничего другого.

При **асинхронном** выполнении вы инициируете операцию (например, асинхронное чтение файла) и сразу получаете управление обратно, чтобы выполнить другие действия. Когда результат операции готов (файл прочитан), программа получает уведомление (например, вызывается коллбэк, завершается Task или высвобождается await) и может обработать результат. Таким образом, поток не простаивает впустую – он либо выполняет другую полезную работу, либо (в случае I/O) вообще может быть освобождён планировщиком на время ожидания данных.

Рассмотрим псевдокод двух сценариев для сравнения:

```csharp
// Синхронный подход:
Console.WriteLine("Начало");
DoLongWork();   // этот вызов блокирует поток until completion
DoLongWork();   // вторая операция начнётся только после завершения первой
Console.WriteLine("Конец");

// Асинхронный подход (с использованием задач):
Console.WriteLine("Начало");
Task task1 = Task.Run(() => DoLongWork());
Task task2 = Task.Run(() => DoLongWork());
// Обе задачи запущены параллельно (на разных потоках из пула)
Task.WaitAll(task1, task2);  // ждём окончания обеих задач
Console.WriteLine("Конец");
```

В синхронном варианте время выполнения суммируется: вторая операция начнётся после первой. В асинхронном варианте две задачи выполняются одновременно, и общее время приближается к длительности более долгой из них (плюс накладные расходы на переключение контекста). В примере для асинхронности мы использовали Task.Run для параллельного запуска операций – по сути задействовали несколько потоков. Однако асинхронность не всегда требует создания новых потоков: если DoLongWork была бы операцией ввода-вывода (например, запрос к веб-серверу), то асинхронный вызов мог бы не занимать поток вовсе во время ожидания ответа, что экономит ресурсы.

Итог: _асинхронность позволяет программе не ждать завершения задачи, а выполнять что-то ещё_. Синхронный же код всегда ждёт. Асинхронный код обычно сложнее отлаживать, но при правильном использовании он делает приложения более эффективными и отзывчивыми.

**Асинхронность с помощью класса Thread**

Один из способов организовать асинхронную работу – напрямую использовать отдельный поток, как мы делали в разделе про многопоточность. По сути, запуск задачи в новом потоке делает её выполнение асинхронным относительно основного потока. Например, если нужно выполнить какую-то операцию в фоновом режиме, мы можем создать Thread для этой задачи. Основной поток при этом продолжит свою работу, не ожидая, пока задача в новом потоке завершится.

Такой подход уже был показан выше. Ещё один упрощённый пример:

```csharp
void ProcessDataAsync()
{
    var thread = new Thread(() =>
    {
        // Долгая обработка данных
        PerformCalculation(); // предположим, длительная операция
        Console.WriteLine("Обработка данных завершена");
    });
    thread.Start();
    Console.WriteLine("Запущена асинхронная обработка данных в отдельном потоке");
    // Метод возвращается сразу, не дожидаясь завершения PerformCalculation()
}
```

Здесь метод ProcessDataAsync() создаёт поток для выполнения функции PerformCalculation() и сразу возвращается (не дожидаясь конца вычислений). Вызвав ProcessDataAsync(), вы делегируете работу фоновому потоку, а сами можете продолжать что-то делать в основном потоке. Позже можно проверить, завершился ли поток, или ожидать его через thread.Join(), или просто позволить ему работать в фоне.

**Недостатки прямого использования Thread для асинхронности:** вам приходится самостоятельно управлять жизненным циклом потока. Нужно следить за количеством запущенных потоков (слишком много — плохо), самостоятельно обрабатывать результаты (нет встроенного механизма вернуть значение из Thread кроме как через общую переменную или callback), ловить исключения (неперехваченное исключение в потоке завершит весь процесс в .NET Framework, в .NET Core/Asp.NET неперехваченные в фоне не убивают процесс, но всё равно их нужно обрабатывать). Также вручную создавать потоки для большого числа мелких задач неэффективно — лучше довериться пулу потоков.

В целом, напрямую создавать потоки имеет смысл, когда нужна тонкий контроль (например, задать _приоритет_ потока, запустить фоновый демонический поток с IsBackground=true и т.п.). В большинстве же случаев в .NET предпочтительно использовать более высокоуровневые абстракции, такие как Task.

**Асинхронность с помощью Task**

Класс Task (пространство имен System.Threading.Tasks) предоставляет абстракцию для асинхронной операции. Task фактически представляет обещание получить результат в будущем (аналогично “promise” в других языках). В отличие от Thread, Task – не обязательно привязан к новому потоку: он может выполняться на потоках из пула или вообще не требовать отдельного потока (например, I/O операции могут выполняться асинхронно на уровне системы ввода-вывода).

Чтобы выполнить задачу асинхронно, чаще всего используется фабричный метод Task.Run(...), который помещает делегат на выполнение в пул потоков. Например:

```csharp
Task task = Task.Run(() => {
    // Код асинхронной задачи (выполняется в пуле потоков)
    Thread.Sleep(1000);
    Console.WriteLine("Задача завершилась");
});

Console.WriteLine("Задача запущена");
// ... здесь может выполняться другой код в основном потоке ...

// Ожидаем окончания задачи (блокирующим ожиданием для примера)
task.Wait();
Console.WriteLine("Основной поток дождался завершения задачи");
```


Этот код делает то же, что и пример с Thread, но через Task.Run. Внутри Task.Run использует поток из _thread pool_. Пул потоков – это набор уже созданных потоков, управляемых средой выполнения .NET, которые переиспользуются для выполнения многих задач. Это гораздо быстрее, чем создавать новый Thread для каждой маленькой работы. В примере мы всё же вызвали task.Wait(), что заставило основной поток подождать завершения задачи – в реальном асинхронном сценарии можно этого и не делать, а продолжать работу и обрабатывать результат задачи когда-нибудь потом (например, через коллбэк ContinueWith или посредством async/await, о чём ниже).

Task бывает двух основных видов:

•Task без типа результата – просто представляет завершение действия (или исключение, если что-то пошло не так).

•Task – задача, которая вернёт результат типа TResult по завершении. Например, Task – результатом будет целое число.

Пример задачи с результатом:

```csharp
Task<int> calcTask = Task.Run(() => {
    // Некоторая длинная вычислительная операция
    int result = HeavyCalculate();
    return result; // Возвращаем значение из задачи
});

// ... здесь можно делать что-то ещё, пока вычисляется result ...

// Получаем результат (блокируя текущий поток до готовности результата)
int calcResult = calcTask.Result;
Console.WriteLine($"Результат вычисления: {calcResult}");
```

В этом примере calcTask.Result будет содержать результат выполнения функции HeavyCalculate(). При доступе к Result текущий поток при необходимости будет ждать завершения задачи. Обратите внимание, если в задаче выброшено исключение, оно будет проброшено при попытке получить Result или вызвать Wait() (в виде AggregateException). Таким образом, Task предоставляет механизм обработки исключений (в отличие от голого Thread, где нужно специально ловить исключения внутри).

Кроме того, у Task есть другие возможности:

•Метод ContinueWith позволяет задать продолжение (callback), которое выполнится после завершения задачи, не блокируя текущий поток.

•Статические методы Task.WhenAll, Task.WhenAny облегчают координацию множества задач (например, ждать завершения всех или любой первой).

Практически, класс Task и связанная с ним _TPL_ (Task Parallel Library) стали стандартом в .NET для написания асинхронного и параллельного кода с момента .NET 4.0. Вручную работать с Thread теперь требуется редко.

**Важное замечание:** хотя Task.Run использует дополнительные потоки для параллельного выполнения, существуют также асинхронные операции, которые выполняются без выделения нового потока. Например, метод File.ReadAllTextAsync() чтение файла асинхронно: под капотом он может использовать Async I/O, при котором поток на время ожидания данных не занят. Task, возвращаемый таким методом, завершится при готовности данных, а всё это время никакой поток не был блокирован впустую. Таким образом, Task является универсальным представлением и для вычислительных задач (требующих потока), и для операций ввода-вывода (не требующих нового потока, но всё равно выполняемых асинхронно).

**Асинхронность с помощью async/await**

Ключевые слова языка C# async и await добавлены, чтобы сделать написание асинхронного кода проще и чище. Они основаны на **Task-based Asynchronous Pattern (TAP)**, то есть работают поверх класса Task. async/await не является альтернативой Task, а скорее удобным способом работать с задачами. Компилятор преобразует методы с async/await в цепочки состояний и коллбэков, что избавляет программиста от необходимости писать такое вручную. Код выглядит почти как синхронный, но выполняется асинхронно.

Как объявить асинхронный метод: достаточно пометить метод модификатором async и внутри него использовать оператор await для вызова других асинхронных операций (возвращающих Task или Task). Такой метод сам будет возвращать Task (или Task если есть возвращаемое значение типа T). Пример:

```csharp
// Асинхронный метод, возвращающий Task<int>
public async Task<int> GetDataLengthAsync(string url)
{
    using HttpClient client = new HttpClient();
    Console.WriteLine("Начинаем асинхронный HTTP-запрос...");
    string data = await client.GetStringAsync(url); // выполнение не блокирует поток
    Console.WriteLine("Данные получены, длина: " + data.Length);
    return data.Length;
}
```

Объяснение: метод GetDataLengthAsync начинается запрос данных по URL. client.GetStringAsync(url) возвращает Task – задачу, которая завершится, когда придёт ответ от сервера. Ключевое слово await перед вызовом означает: _вызови эту асинхронную задачу и не блокируй текущий поток; когда задача завершится, возобнови выполнение этого метода, получив результат_. Пока идёт сетевой запрос, поток, выполняющий метод, может делать другие вещи (в UI-приложении управление вернётся циклу сообщений, не замораживая интерфейс; на сервере этот поток может быть возвращён в пул). Когда ответ получен, выполнение метода продолжится с той строчки, где стоял await, переменная data получит результат. Затем мы выводим длину данных и возвращаем её. Компилятор C# перепишет этот метод в более сложную структуру (с разбитием на два метода: до await и после, с объектом-континуейшеном). Но для разработчика это прозрачно – код пишется в привычном последовательном стиле.

Использование async-метода:

```csharp

async Task DemoAsyncAwait()
{
    Console.WriteLine("Вызываем асинхронный метод...");
    Task<int> task = GetDataLengthAsync("http://example.com/data");
    Console.WriteLine("Асинхронный метод запущен, можно выполнять другую работу...");

    // ... тут может быть другая работа, пока ждем данных ...

    int length = await task; // ожидаем завершения задачи (не блокируя текущий поток)
    Console.WriteLine($"Длина полученных данных: {length}");
}
```

Здесь мы вызываем GetDataLengthAsync и сразу получаем Task (управление возвращается немедленно). Мы могли бы пока сделать что-то ещё. Затем с помощью await task мы асинхронно ожидаем результата – текущий метод DemoAsyncAwait при этом тоже становится асинхронным (возвращает Task). Когда выполнение дойдёт до await task, метод приостановится, возвращив управление вызвавшему коду, и продолжится только после получения результата task. Заметим, ни один поток здесь **не блокируется** ради ожидания – ожидание осуществляется неблокирующим образом. Это ключевое отличие от вызова task.Wait() или task.Result, которые бы блокировали поток.

**Преимущества async/await:** значительно упрощает управление сложными асинхронными последовательностями операций. Вместо пирамиды коллбэков или цепочек ContinueWith, код пишется как последовательный, а компилятор разбирается с остальным. Также await автоматически перенаправляет возникшие внутри исключения – они просто выбрасываются из асинхронного метода при ожидании, и могут быть пойманы обычным try/catch снаружи.

**Важно:** при использовании async/await нужно следить за тем, чтобы не смешивать синхронный и асинхронный код неправильно. Если вызвать асинхронный метод и забыть await (или аналогичного механизма), можно непреднамеренно продолжить выполнение, не дождавшись результата. В GUI-приложениях метод, вызываемый через await, по умолчанию продолжит выполнение на исходном (UI) потоке после ожидания, благодаря механизму _SynchronizationContext_. А вот в консольных приложениях или ASP.NET продолжение может выполниться на пуле потоков. В целом, правило – “асинхронность от начала до конца”: верхнеуровневые вызовы тоже должны быть асинхронными (например, обработчики событий в WinForms/WPF могут быть async void, а в ASP.NET контроллеры – async Task). Если где-то посреди цепочки вызвать .Wait() или .Result, это блокирует поток и может привести к deadlock (особенно известная проблема блокирования UI-потока). Поэтому лучше **полностью придерживаться async/await**, не смешивая с блокирующими ожиданиями.

В итоге, **асинхронность в C#** чаще всего реализуется через комбинацию Task + async/await. Этот подход покрывает большинство случаев, позволяя писать эффективный и понятный код. Однако, асинхронный код не обязательно выполняется параллельно на нескольких ядрах – если задачи CPU-интенсивные и вы хотите ускорить их выполнение, нужно рассмотреть параллелизм. Далее мы поговорим о параллелизме и специальных конструкциях для него.

**Параллелизм**

**Параллелизм** – это выполнение нескольких задач одновременно в один и тот же момент времени. Если асинхронность больше про эффективное планирование (не ждать бездельно, а переключаться между задачами), то параллелизм – про одновременное использование нескольких вычислительных ресурсов. В контексте .NET параллелизм обычно достигается с помощью распределения работы между несколькими потоками, работающими на разных ядрах.

Пример параллелизма из жизни – если асинхронность мы сравнивали с одним человеком, переключающимся между задачами, то параллелизм – это когда **несколько человек** выполняют разные задачи в одно время. Например, один человек готовит суп, в то же время другой человек жарит рыбу, и третий накрывает на стол. Это действительно одновременное выполнение, позволяющее закончить дело быстрее, но требующее достаточного количества ресурсов (нескольких людей) и координации (чтобы не мешать друг другу).

В C# для параллельного программирования предоставлены удобные средства в пространстве имен System.Threading.Tasks – это класс Parallel и технология PLINQ (Parallel LINQ). Эти высокоуровневые API позволяют легко распараллелить независимые фрагменты работы, абстрагируясь от ручного создания и управления потоками. Под капотом они используют тот же пул потоков и задачи Task. Рассмотрим основные возможности:

**Parallel LINQ (PLINQ)**

**PLINQ** (Parallel LINQ) – это параллельная версия LINQ-to-Objects. Идея проста: если у вас есть операция над коллекцией (например, выбрать из массива все элементы по условию и преобразовать их), то можно автоматическом режиме разбить эту работу на несколько потоков. PLINQ делает это, когда вы используете метод расширения .AsParallel() для последовательности. Остальная часть LINQ-запроса затем выполняется параллельно.

Например, вычислим суммы квадратов чисел от 1 до 1\_000\_000 последовательно и параллельно:

```csharp

int[] data = Enumerable.Range(1, 1_000_000).ToArray();

// Обычный LINQ (синхронно, в одном потоке)
int sumSeq = data.Where(x => x % 2 == 0).Sum(x => x * x);

// Параллельный LINQ (PLINQ)
int sumPar = data.AsParallel()
                 .Where(x => x % 2 == 0)
                 .Sum(x => x * x);

Console.WriteLine($"Результат последовательный: {sumSeq}, параллельный: {sumPar}");
```

В приведённом примере AsParallel() просит среду выполнить последующие операции (Where и Sum) в параллельном режиме. Коллекция автоматически разделится на части, которые обрабатываются в разных потоках, а результаты будут агрегированы. Переменные sumSeq и sumPar должны получиться равными (параллельный и последовательный подход дают одинаковый результат), но параллельный, вероятно, выполнится быстрее на машине с несколькими ядрами, потому что фильтрация и суммирование происходят одновременно в нескольких потоках.

PLINQ особенно полезен для преобразования больших объемов данных в памяти, когда каждую элементарную операцию можно делать независимо. Например, обработка каждого элемента массива – кандидат для параллелизма. При этом PLINQ сам решает, как оптимально распараллелить, сколько потоков задействовать (обычно соответствует числу доступных ядер) и т.д. Можно указывать дополнительные опции, например: .AsParallel().WithDegreeOfParallelism(4) – ограничить число потоков, или .AsParallel().AsOrdered() – сохранить порядок следования элементов как в исходной последовательности (по умолчанию PLINQ может возвращать результаты в неопределённом порядке для скорости).

Стоит помнить, что параллелизация имеет накладные расходы на координацию потоков, поэтому на малых объемах данных или простых операциях параллельный вариант может быть даже медленнее последовательного из-за оверхеда. PLINQ следует применять, когда работа на каждый элемент достаточно тяжёлая или количество элементов велико, и у системы есть свободные ядра.

**Parallel.ForEach**

Метод Parallel.ForEach предоставляет императивный подход к параллельной обработке коллекции. Он пробегает по коллекции (или любому IEnumerable) и выполняет указанное действие для каждого элемента **в параллельном режиме**. В отличие от обычного foreach, который обрабатывает элементы последовательно, Parallel.ForEach разделит итерации между несколькими потоками.

Пример использования Parallel.ForEach:

```csharp
string[] urls = { "http://example.com/1", "http://example.com/2", "http://example.com/3" };

Parallel.ForEach(urls, url =>
{
    // Каждая итерация может выполняться в отдельном потоке из пула
    string data = new WebClient().DownloadString(url);
    Console.WriteLine($"Загружено {data.Length} байт с {url} (поток {Thread.CurrentThread.ManagedThreadId})");
});
```

Здесь для каждого URL происходит загрузка данных. Три загрузки будут выполняться одновременно на разных потоках, что потенциально ускорит общую работу (в данном примере узким местом, вероятно, будет сам интернет-канал, но при наличии нескольких ядер и хорошего канала эти загрузки параллелятся). Parallel.ForEach вернется после того, как все итерации завершатся (то есть, по завершении всех загрузок). Порядок выполнения итераций не определён – они могут стартовать в любом порядке и завершаться независимо. Если важен порядок или нужен сбор результатов, можно использовать потокобезопасные коллекции (например, ConcurrentBag внутри цикла, либо параллельный LINQ, который лучше управляет порядком).

Стоит отметить: Parallel.ForEach блокирует текущий поток, пока не выполнит все итерации (то есть, это _синхронный_ вызов в том смысле, что после него код продолжится только когда всё будет готово, хотя внутри он делал параллельно). В отличие от асинхронных методов, Parallel.ForEach не возвращает Task и не предполагает await. Поэтому Parallel.ForEach хорошо подходит для ситуаций, где нужно параллельно обработать коллекцию прямо здесь и сейчас, а продолжать работу можно только зная, что всё завершено. Если же нужно запустить параллельную обработку и не ждать её окончания немедленно, можно обернуть вызов Parallel.ForEach в Task.Run или использовать аналогичные асинхронные паттерны.

Пример параллельной обработки чисел с накоплением результата (с учётом потокобезопасности):

```csharp
int[] numbers = Enumerable.Range(1, 1000000).ToArray();
long total = 0;

// Параллельно суммируем квадраты чисел (используем Interlocked для безопасности при доступе к total)
Parallel.ForEach(numbers, num =>
{
    long square = (long)num * num;
    Interlocked.Add(ref total, square);
});

Console.WriteLine($"Сумма квадратов = {total}");
```

Здесь каждый поток вычисляет квадрат числа и добавляет в общую сумму total. Используется Interlocked.Add для атомарного сложения, чтобы избежать условий гонки на переменной total. Это пример того, как при параллельной обработке нужно быть осторожным с общими данными. Альтернативно, можно было собрать результаты в потокобезопасную коллекцию и потом объединить, или воспользоваться PLINQ: numbers.AsParallel().Sum(x => (long)x \* x).

**Parallel.For**

Parallel.For похож на Parallel.ForEach, но предназначен для классических счетных циклов. Он позволяет выполнить итерации от начального значения до конечного с параллельным разделением диапазона. Синтаксис: Parallel.For(startInclusive, endExclusive, body). Например:

```csharp
int n = 10000000;
long sum = 0;
Parallel.For(0, n, i =>
{
    // Здесь также необходимо безопасно обновлять общую переменную
    Interlocked.Add(ref sum, i);
});
Console.WriteLine($"Сумма чисел от 0 до {n-1} = {sum}");
```

Этот код параллельно складывает все числа от 0 до n-1. Работу разделяет сама функция Parallel.For: диапазон разбивается на части между потоками. Внутри мы снова используем Interlocked.Add для потокобезопасного обновления суммы. Parallel.For также блокирует вызывающий поток до завершения всех итераций (то есть, управляет своим параллелизмом внутри).

У Parallel.For есть перегрузки, позволяющие:

•Определять локальные начальные значения для каждого потока (Parallel.For(..., () => localInit, (i, state, local) => { ...; return local; }, localFinal => { ... })), которые можно использовать для накопления результатов без синхронизации, а потом объединять в localFinal. Это полезно, чтобы уменьшить потребность в синхронизации на каждой итерации.

•Досрочно прервать цикл – метод может принимать объект ParallelLoopState, через который можно вызвать state.Break() (чтобы запросить остановку после определённой итерации) или state.Stop() (чтобы прервать выполнение как можно скорее).

Но в базовом случае Parallel.For применяется для простого распараллеливания традиционных for-циклов. Например, можно параллельно инициализировать элементы массива, параллельно применять формулу к каждому индексу и т.д.

**Parallel.Invoke**

Если Parallel.ForEach и Parallel.For предназначены для однотипных действий над набором данных, то Parallel.Invoke удобен, когда нужно параллельно выполнить **несколько разных действий или методов**. Он принимает набор делегатов Action и запускает их все одновременно, ожидая, когда все завершатся.

Пример использования Parallel.Invoke:

```csharp
void MethodA() { /* какая-то работа */ }
void MethodB() { /* другая работа */ }

// Выполним MethodA, MethodB и лямбда-выражение параллельно:
Parallel.Invoke(
    () => MethodA(),
    () => MethodB(),
    () => {
        Console.WriteLine("Выполняется задача C");
        Thread.Sleep(500);
        Console.WriteLine("Задача C завершена");
    }
);
Console.WriteLine("Все параллельные задачи завершены");
```


В этом примере три задания (две именованных функции и одна анонимная) будут выполняться параллельно. Метод вернётся только когда все три завершатся. Порядок начала может быть любым, результаты независимы. Это проще, чем вручную создавать три Task или Thread и потом ждать их завершения. Внутри Parallel.Invoke также использует пул потоков.

Parallel.Invoke полезен, когда у вас есть, скажем, несколько длительных операций, которые можно делать одновременно: например, параллельно считать данные из базы, генерировать отчет и обрабатывать пользовательский ввод (хотя в GUI среде вы бы не делали это через Parallel.Invoke на UI-потоке). В серверных приложениях можно параллельно вызывать несколько внешних сервисов и собрать результаты, ускорив общее время отклика (но тут надо сравнить с асинхронным ожиданием всех результатов; Parallel.Invoke будет занимать потоки).

**Отметки о параллелизме и потокобезопасности**

Когда используете Parallel.ForEach, Parallel.For или Parallel.Invoke, помните, что код внутри них выполняется на нескольких потоках одновременно. Все проблемы классической многопоточности (гонки данных, необходимость синхронизации доступов к общим переменным, состояние) остаются в силе. Высокоуровневые API не освобождают от этих нюансов, они лишь упрощают разбиение работы. Поэтому:

•Избегайте изменения разделяемых переменных из нескольких параллельных задач без синхронизации. Лучше организовать вычисления так, чтобы каждое параллельное действие имело свои локальные результаты, а затем объединить их.

•Если нужно обновлять общий объект из параллельных секций, используйте потоко-безопасные коллекции (ConcurrentDictionary, ConcurrentBag, и т.д.) или примитивы синхронизации (lock, Interlocked, etc.).

•Следите за нагрузкой: запуск слишком интенсивного параллелизма может нагружать CPU на 100%, что не всегда желаемо (можно ограничить степень параллелизма параметрами).

**Сравнение подходов**

Мы рассмотрели множество способов организации одновременного выполнения кода. Подведём итоги и сравним ключевые подходы друг с другом.

**Thread vs Task**

•**Уровень абстракции:** Thread – низкоуровневый объект операционной системы (представляет реальный поток выполнения). Task – высокоуровневое представление асинхронной операции, абстракция над одним или несколькими действиями, которые могут выполняться на пуле потоков или иным способом.

•**Создание и планирование:** При создании Thread вы явно создаёте новый поток (т.е. ОС будет планировать ещё одну единицу выполнения). Task по умолчанию берёт поток из пула (через Task.Run), то есть переиспользует существующий. Создание и запуск Task имеет меньше накладных расходов, чем создание нового Thread. Библиотека управления задачами может самостоятельно решать, когда и на каком потоке выполнить задачу.

•**Возврат результатов:** У Thread нет встроенного механизма вернуть результат работы (можно, например, записать в общую переменную или использовать Thread.Join() в сочетании с состоянием). Task изначально может иметь результат – тип Task позволяет получить результат через свойство .Result (или при await этот результат просто возвращается).

•**Обработка исключений:** Если в потоке происходит неперехваченное исключение, в .NET Framework это падение приложения; в .NET Core потоки по умолчанию “съедают” исключение, но его трудно отследить. Task же аккумулирует исключение и вы получите его при ожидании задачи (через .Wait()/.Result или в await оно выбросится). То есть, Task предоставляет более безопасную и удобную модель обработки ошибок.

•**Синхронизация и состояние:** Сам по себе Thread ничего не знает о других потоках, вам нужно вручную координировать их (например, использовать ManualResetEvent или lock). Для задач Task есть удобные методы продолжений (ContinueWith), а при использовании async/await координация последовательности задач вообще выражается естественным кодом. Кроме того, задачи можно комбинировать (Task.WhenAll и т.п.), что упрощает управление множеством параллельных операций.

•**Отмена:** Оба поддерживают отмену, но с Task это встроено лучше через CancellationToken. Поток тоже можно прервать, но Thread.Abort считается небезопасным и устаревшим. Обычно отмена реализуется добровольно внутри задач, периодически проверяя токен отмены.

•**Использование:** Рекомендуется использовать Task (и связанные высокоуровневые API) для большинства сценариев, так как они упрощают разработку и более эффективно используют ресурсы. Использовать Thread напрямую стоит, когда у вас особые требования (например, нужен конкретный STA поток, особый приоритет, длительно живущий фоновый поток и т.п.).

**Вывод:** _Task – более высокоуровневый и удобный инструмент, чем Thread._ В современных .NET приложениях прямое создание потоков встречается редко – обычно работают с задачами и async/await. Однако понимание работы потоков важно, ведь задачи в конечном счёте выполняются на потоках.

**Task vs async/await**

Сравнивать Task и async/await не совсем корректно напрямую, потому что это **разные уровни** одной концепции: async/await – синтаксический сахар языка, а Task – класс библиотеки. Тем не менее, рассмотрим различия в подходе написания кода с их использованием:

•**Стиль программирования:** Без async/await взаимодействие с задачами требует либо блокировать поток (task.Wait()/.Result), либо использовать коллбэки (ContinueWith). Это может приводить к менее читабельному и более сложному коду, особенно при цепочке асинхронных операций (callback hell). async/await позволяет писать асинхронный код в императивном стиле, как будто он синхронный – что значительно упрощает чтение и поддержку.

•**Необходимость вручную координировать:** С async/await компилятор и runtime берут на себя большую часть координации – вам не нужно писать код, который после завершения одной задачи запускает другую: достаточно написать последовательность с await. Без await вам бы пришлось вручную подписываться на завершение (ContinueWith или использовать Task.WhenAll/WhenAny), что больше кода и больше шансов на ошибку.

•**Ошибка при забытом ожидании:** При использовании Task напрямую легко забыть дождаться выполнения (например, запустили Task.Run и не вызвали Wait() или не использовали результат). В случае async методов, если вы не используете результат (await или .Wait()), компилятор может выдать предупреждение, т.к. проигнорированный Task потенциально означает незавершённую операцию. То есть, async/await побуждает правильнее обращаться с задачами.

•**Совместное использование:** Практически всегда async/await и Task применяются вместе. Вы не можете использовать await, не имея Task (или аналогичных типов, реализующих GetAwaiter). И наоборот, просто Task без await – часто неудобен. Поэтому обычно выбор стоит не “или-или”, а **как комбинировать**: например, CPU-bound задачи вы можете запускать через Task.Run внутри async метода и затем await их.

•**Когда не использовать async/await:** Бывают случаи, когда использовать async/await сверху нет смысла. Например, метод, который просто сразу запускает несколько задач и возвращает объединённую задачу:

```csharp
Task ProcessAllAsync() 
{
    var t1 = DoWork1Async();
    var t2 = DoWork2Async();
    return Task.WhenAll(t1, t2);
}
```

Тут мы вовсе не использовали await – и правильно, метод сразу возвращает задачу, и вы можете её await-нуть снаружи. Если бы мы написали этот метод как async Task ProcessAllAsync() { await DoWork1Async(); await DoWork2Async(); }, результат был бы тот же, но мы создали бы лишнюю машину состояний. В общем, async/await – инструмент для удобства, но его избыточное употребление (там, где можно обойтись комбинацией задач) нежелательно.

**Вывод:** _async/await делает использование задач проще и менее ошибкоопасным._ В большинстве случаев при работе с Task-ами в приложениях на C# стоит использовать async/await, чтобы писать понятный код. Но помнить, что под капотом все равно работают Task (или похожие структуры) – полезно для понимания производительности и поведения. Например, зная это, вы не будете пытаться выполнить CPU-bound вычисление внутри async-метода без выделения отдельного потока (ведь тогда он будет выполняться на том же потоке и блокировать его). В таких ситуациях правильно сочетать Task.Run и await.

**Когда использовать что: рекомендации**

Наконец, обобщим рекомендации, какой подход применять в разных ситуациях:

•**Долгие ввод-вывод (I/O) операции, ожидающие внешних откликов** – используйте **асинхронность с async/await**. Например, сетевые запросы, обращения к базе данных, чтение/запись файлов. Это позволит не блокировать потоки во время ожидания и масштабировать приложение (веб-сервер сможет держать больше одновременных запросов, UI-приложение не «замёрзнет» во время загрузки). Новый поток здесь не нужен, асинхронные методы сами позаботятся об ожидании.

•**Вычислительно интенсивные задачи (CPU-bound), которые можно распараллелить** – используйте **Parallel.For/ForEach/Invoke или PLINQ** для простого разделения нагрузки на ядра, либо распараллеливайте с помощью запуска нескольких задач Task вручную. Например, обработка большого массива, рендеринг, математические расчёты – все, что грузит процессор, стоит распределить по потокам. Здесь Parallel-методы особенно удобны, если задача подходит под шаблон (есть коллекция или диапазон). Если шаблон не подходит, можно просто создавать несколько задач Task.Run для независимых частей работы и затем ожидать их завершения (await Task.WhenAll(...) или Parallel.Invoke).

•**Не очень долгий фоновой процесс, после которого нужен результат** – лучше оформить как **async метод, возвращающий Task**. Внутри него, если это CPU-работа, выполнить через Task.Run, если I/O – напрямую await-на нужный Async метод. Например, вычислить что-то без замораживания UI: int result = await Task.Run(() => Compute());.

•**Низкоуровневый контроль над потоками** – используйте **Thread**. Это узкие случаи: например, вам нужен поток в отдельном _Apartment_ (STA) для взаимодействия с COM-объектом или вы пишете свой планировщик потоков. В общем, если вам не подходят абстракции Task/Parallel, только тогда беритесь за ручное управление потоками.

В целом, **асинхронность** и **параллелизм** дополняют друг друга. Асинхронность (особенно с async/await) помогает эффективнее использовать один поток и не держать его в ожидании. Параллелизм (многопоточность, Parallel API) помогает использовать несколько потоков для разделения работы. В комплексе, эти технологии позволяют создавать производительные и отзывчивые приложения на C#.
